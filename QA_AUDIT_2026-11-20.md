## One-page verdict

**Do NOT send this to the client as-is. The FBR invoice layout is a faithful match to the client's sample, and the new code is cleanly written — but the build has five blockers that must be fixed first, and the pre-existing money/security holes from Nov 16 are all still open.**

**MUST fix before client delivery:**
1. **Rotate the committed OpenRouter API key and purge it from git history** — still tracked in `scratch/test-openrouter.js`, live-format, since `8f46bb8`. Anyone with repo access can spend the owner's OpenRouter account. (C1)
2. **Decide the GST question and store GST at checkout** — the printed invoice demands 18% MORE than the customer paid. A POS sale of 138,980 prints an invoice for 163,996.40. The invoice is currently not a record of the transaction. (C4)

**What is genuinely good:** the invoice matches the sample field-for-field (layout, meta, items table, totals placement, FBR 3×2 grid, Amount in Words for the sample amount); the new code added **zero** lint problems (all 8 new files lint clean, no `any`); the new invoice lookup is org-scoped; `updateFbrSettings` is the best-validated action in the repo; the radars' 4–6 month expiry bands work as specified; the dashboard diff is purely additive with no regressions; the build passes with TypeScript clean.

## Critical

### C1 — Live-format OpenRouter API key still committed and tracked (S1, HOLDS, unchanged)
`scratch/test-openrouter.js:1` still contains a 73-char `sk-or-v1-…` key; `git ls-files` still lists the file; only commit touching it is still `8f46bb8`. Repo-wide grep for other live keys (`sk-or-v1-`, `sk-ant-`, `ghp_/gho_`, `AKIA`, PEM blocks) found nothing else. No `.env*` file exists in the repo.
**Impact:** anyone with repo access can spend/abuse the owner's OpenRouter account.
**Fix:** revoke/rotate the key in OpenRouter, delete the file, purge it from git history (deletion alone is insufficient — it stays in history).

### C2 — Still no RLS / schema / migrations in the repo; the setup SQL now codifies "NO RLS" (S2, HOLDS, worse)
Still no `supabase/` directory, no `.sql` file, no `create policy` / `enable row level security` anywhere in the repo. The new single-file setup `~/workspace/your_files/pos-full-setup.sql` (776 lines, 21 tables) states in its header (lines 38–42): "NO RLS: the tables are created WITHOUT Row Level Security, on purpose… RLS hardening is a separate job." Section Y then grants `select, insert, update, delete on all tables in schema public to anon, authenticated`, plus `alter default privileges…`. The anon key the app uses (`lib/supabase/server.ts`, `lib/supabase/client.ts`) therefore has full DML on every table via PostgREST with no DB-level tenant check. It does add `organization_id` columns and a per-org unique index `(organization_id, invoice_number)`, but no policy constrains *which* org's rows a JWT can touch.
**Impact:** if the live project was built from this file (as intended), every RLS-conditional finding in this report is live, not theoretical: any valid JWT can read/write any tenant's rows directly through PostgREST, bypassing all app-level role checks and org filters. The no-RLS posture is now the documented deployment, not an accident.
**Fix:** add RLS policies (at minimum `organization_id = (auth.jwt() -> profiles -> organization_id)` per table, plus a service-role-only rule for `organizations.fbr_token`) as migrations in the repo and verify against the live project; until then treat the app as single-tenant-only.

### C3 — Checkout still non-atomic, still trusts all client-supplied money, still reports success on partial failure (S8/B1/B2, HOLDS, unchanged)
`app/actions/sales.ts:53-72,121-127,148-185`: `unit_price`/`subtotal`/`totalAmount` come straight from the POS cart; the server never re-reads `products.selling_price`, never verifies product/customer org, never checks stock. The sale header is inserted first, then `sale_items` + `inventory_movements` are `Promise.all`'d (`:170`); failures are only `console.error`'d (`:174-178`) and `:185` still returns `{ success: true, invoice_number }`. POS then shows "Sale completed and stock deducted successfully" (`pos-client.tsx:378-380`). `pos-client.tsx:51-67` (`addToCart`) has no stock cap or quantity limit. Still zero `.rpc()` calls anywhere in `app/`/`lib/`/`components/` (grep count 0) — no transaction for any multi-step write. Still no `checkAccess` in `sales.ts` (count 0).
**Impact:** a paid sale can exist with no line items and no stock deduction; a tampered request can sell at $0.01 with an arbitrary total; overselling to negative stock is possible; stock and revenue silently diverge with no retry/compensating path.
**Fix:** re-price server-side from `products`, verify org + stock, wrap sale+items+movements+customer-total in one Postgres transaction (`.rpc()`), and return failure if any leg fails.

### C4 — Invoice Grand Total ≠ amount actually charged/paid: GST added on top of an ex-GST POS total (NEW, introduced e35d033/846e02a)
POS cart total is `Σ qty × unit_price` with **no GST at checkout** (`app/(dashboard)/sales/pos/pos-client.tsx:85`); `processCheckout` stores `subtotal = total_amount = totalAmount` (`app/actions/sales.ts:168-169`). The invoice then recomputes `subtotal = Σ item.subtotal`, per-line `GST = round2(line × gstRate)`, `grandTotal = subtotal + gstTotal` (`app/(dashboard)/sales/invoices/[id]/fbr-invoice-client.tsx:159-164`) and **ignores `sale.subtotal`/`sale.total_amount` entirely**. Verified by execution: a POS sale of 138,980 invoices at **163,996.40**. To reproduce the sample's Grand Total of 138,980 the POS total would have to be 117,779.66 (138,980 ÷ 1.18 — a non-round price). Reports/P&L and `total_spent` sum the ex-GST `total_amount`, so revenue is understated by GST vs what was invoiced. Per-line rounding (round each line, then sum) can also differ by cents from `round2(subtotal × rate)`.
**Impact:** every printed invoice overstates what the customer paid by 18%; the invoice is not a record of the transaction.
**Fix:** decide once whether POS prices are GST-inclusive (invoice GST = total × 18/118, grand = amount paid) or GST-exclusive (add GST at checkout, store `gst_amount`/`grand_total`, invoice and reports read the stored values, never recompute).

### C5 — Invoice page 404s for every invoice until the v2 delta SQL runs (NEW, e35d033)
`getInvoiceByNumber` (`app/actions/sales.ts:257-265`) selects `procurement_ref, fbr_status, fbr_reference_no, fbr_response_code, fbr_response_message, fbr_submitted_at`, `customers(ntn, buyer_type)`, `products(weight)`. On **any** error it returns `null` (`:270-280`) and `invoices/[id]/page.tsx:14` calls `notFound()`. If the 13 v2 columns don't exist yet, the query errors and **all** invoice pages 404 — including old pre-v2 sales. The checkout insert never references the FBR columns (`sales.ts:143-153`), so sales succeed while their invoices are unreadable. `updateFbrSettings` similarly fails with "column does not exist" (acknowledged in its own comment, `organization.ts:121-128`).
**Impact:** the new page is a hard regression vs the old invoice until the delta is run on the live DB.
**Fix:** run `fbr-invoice-v2-delta.sql` on the live DB; defensively, make the fetch fall back to a column-safe select (or a plain-language "schema update needed" message) instead of 404ing on any error.

## High

### H1 — NEW: FBR token is delivered to every signed-in user's browser, contradicting "backend-only" (introduced e35d033/846e02a)
Chain, verified independently by four auditors:
- `app/actions/organization.ts:27-33` `getOrganization()` does `.select('*')` on `organizations` — includes `fbr_token` — with only a "profile exists" check, no role check.
- `lib/auth-utils.ts:22-31` `getOrganization(organizationId)` also does `.select('*')` with no membership check.
- `app/(dashboard)/layout.tsx:12-17` passes the full row as `initialOrganization` to `OrganizationProvider`, a `'use client'` component (`components/providers/organization-provider.tsx:1,33-46`) whose `OrganizationData` type explicitly includes `fbr_token?: string | null` (line 15). RSC props to client components are serialized to the browser — so **every** signed-in user, including `employee`, receives the token in page data on every dashboard load. The provider also rebroadcasts the full object on `window` via `CustomEvent('qurbat-organization-updated')` (lines ~70-80, ~100-115).
- Same leak on two more paths: `app/(dashboard)/sales/invoices/[id]/page.tsx:9-18` passes the `select('*')` row into `FbrInvoiceClient` (client component); `app/actions/organization.ts:145-152` `updateFbrSettings` returns the full updated row (`.select().single()`) including the token.
- Mitigating facts: `fbr-invoice-client.tsx` never renders the token (lines 18, 136-139 state it explicitly; QR renders only from `fbr_reference_no`, lines 174-180); the Settings form masks it with `type="password"` (`settings-client.tsx:1001-1010`); Settings layout gates to admin/owner. But masking in one form does not undo serialization to the browser. The token is also stored **plaintext** in the DB (`organization.ts:136`).
**Impact:** the FBR credential is exposed to all org users (and any XSS/browser extension), not just owner/admin; anyone holding it can submit invoices as the business to FBR. (Whether a real token is currently stored live is unverifiable from code — if empty, this is latent rather than actively leaking, but the code path ships whatever is stored.)
**Fix:** never `select('*')` on `organizations`; enumerate columns and exclude `fbr_token` everywhere except the server-only FBR submission path (which does not exist yet); store the token encrypted or in Vault, not plaintext in a column readable by the anon key.

### H2 — Read actions without org filter got worse: 24 of 30 reads unfiltered (S4, HOLDS, WORSE)
Recounted at `ba3484a` across all exported functions in `app/actions/*.ts` (function-by-function, checking for `organization_id` in each body). Unfiltered reads: `dashboard.ts` `getCheeseCommandCenterData`, `getExecutiveDashboardStats`; `employees.ts` `getEmployees`, `getAttendance`, `getEmployeeAttendanceHistory` (incl. salaries); `expenses.ts` `getExpenseCategories`, `getExpenses`; `inventory.ts` `getCategories`, `getProducts`, `getStockLevels`, `getMovements`, `getBatches`, `getDashboardStats`; `purchases.ts` `getPurchaseOrders`; `returns.ts` `getReturns`; `sales.ts` `getCustomers`; `payroll.ts` `getPayroll`; `vendors.ts` `getVendors`, `getVendorOrders`; plus all 5 new radar reads. Filtered reads are only `getOrganization`, `getComprehensiveReports`, `getInvoiceByNumber`, `getTasks`, `getAssignees`. (Old count was 18/25; the 5 new radar reads plus `getDashboardStats`/`getExecutiveDashboardStats` account for the growth.) All use the anon-key client, so with no RLS (C2) any signed-in user gets every tenant's rows.
**Fix:** add `.eq('organization_id', profile.organization_id)` to every read (or, better, enforce it in RLS and keep the app filter as defense-in-depth).

### H3 — NEW: all radar actions have zero auth and zero org filter; only the page is gated (7dfa641)
`app/actions/radars.ts:1-12` header comment admits it: "no org filter is added here, matching those files. The wider RLS / org-filter gap is a known repo issue, not fixed in this build." Verified: `getExpiryRadar` (delegates to unfiltered `getBatches`), `getStockRadar` (→ unfiltered `getStockLevels`), `getInventoryRadar` (`radars.ts:283-300`, direct unbounded `inventory_movements` select, no org filter, no auth), `getVendorsRadar` (`radars.ts:352-372`, direct unbounded `vendors` + `purchase_orders` selects), `getRadarSummary` (delegates to the above). `grep -c checkAccess app/actions/radars.ts` = 0; no `getUserProfile`/`getUser` call anywhere in the file. The page gate exists (`app/(dashboard)/radars/page.tsx:22` `checkAccess(['owner','admin','manager'])`, sidebar hides Radars from employees at `components/app-sidebar.tsx:398-409`), and the dashboard strip correctly suppresses the summary for employees (`app/(dashboard)/dashboard/page.tsx:17-19`) — but server actions are directly callable, so any signed-in `employee` can invoke them and receive **all tenants'** batches, stock, movements, vendors and POs. No user input is taken, so there is no injection surface here; the exposure is purely auth/tenancy. Radars add no new writes (read-only) and no unchecked inserts.
**Impact:** beyond the security exposure, radar counts on `/radars` and the dashboard strip are wrong for any multi-tenant DB — they mix all tenants.
**Fix:** require profile + org filter inside each radar action (and in the `getBatches`/`getStockLevels` helpers they delegate to); do not rely on the page gate.

### H4 — Manager can still promote anyone (including self) to `owner` (S7, HOLDS, unchanged)
`app/actions/employees.ts:40` takes `system_role` raw from FormData (no whitelist); `createEmployee` is gated admin/owner (`:25`) but writes it into `profiles.role` (`:96-104`). `updateEmployee` is gated to `['admin','owner','manager']` (`:135`) and `:150,172-177` writes raw `system_role` into any linked profile — a manager can promote self to owner, then use the owner-only AI agent. `base_salary` is still unvalidated `parseFloat` (`:33,143`).
**Fix:** whitelist `system_role` to `['owner','admin','manager','employee']` and require `owner` role to set anything above the caller's own role (managers may not touch `role` at all).

### H5 — Invoice serials improved but the race is NOT fixed (B3, PARTIALLY FIXED, still High)
Old `INV-<Date.now last 6>` is gone. New `generateSequentialInvoiceNumber` (`app/actions/sales.ts:59-105`): reads the org's `invoice_prefix` (default `GT-226`), fetches **all** matching `sales.invoice_number` rows (unbounded, no `.limit()`), takes max suffix + 1. Plain read-then-write — the code's own comment (lines 69-71) admits two simultaneous checkouts can read the same max. No DB sequence, no retry. Backstop exists only in the workspace SQL, not the repo: `pos-full-setup.sql:719` creates `sales_org_invoice_key` unique on `(organization_id, invoice_number)` — but `fbr-invoice-v2-delta.sql` does **not** create it, and whether the live DB (built from the Nov-16 file) has it is unverifiable without live access. If the index exists, the second concurrent checkout fails cleanly (error returned, user must redo checkout — no retry logic). If it doesn't, duplicate serials persist and `getInvoiceByNumber(...).maybeSingle()` (`sales.ts:255-272`) breaks. Also: changing the prefix restarts the sequence at 0001; `RET-` numbers still use `Date.now().slice(-6)` (`returns.ts:66`); the AI executor still mints `INV-<Date.now…>` (`lib/ai/executor.ts:1162`), bypassing the new scheme entirely.
**Fix:** DB sequence per org (or `INSERT … ON CONFLICT` retry loop, max ~5 attempts) + add the unique index to the delta SQL and verify it exists live + route the AI executor through the same generator.

### H6 — "Copy for FBR" is not an FBR-portal format (NEW, e35d033/846e02a)
`buildFbrText()` (`fbr-invoice-client.tsx:~205-268`) builds human-readable plain text (seller, buyer, items, totals, FBR block, Important note, signatures); `buildFbrHtml()` just wraps it in `<br>`s. The button label and the "formatted to paste into the FBR portal" comment overclaim. It also copies the H2 placeholder bracket text when fields are unset.
**Impact:** the user will paste free text into a portal that expects structured/API submission; submission will fail or be meaningless.
**Fix:** relabel "Copy invoice text"; do not claim portal submission; build the real FBR submission only once the FBR/PRAL integration spec and token arrive.

### H7 — Template placeholder text prints on real invoices when fields are unset (NEW, e35d033/846e02a)
Seller NTN `[Enter registered number]`, bank `[Bank name]`, IBAN `[Masked account / IBAN details]` (`fbr-invoice-client.tsx:445,451`, seller block ~:420s), buyer NTN `[Enter buyer number, if applicable]` / Buyer Type `[Confirm applicable FBR category]` — the sample's bracketed placeholders reproduced as live fallbacks, and they render **in the printout**, not just on screen. The client has not provided NTN, bank name, or IBAN yet, so the first live invoice will print them. Dispatch also defaults to a fabricated fact: `organization?.dispatch_text || 'Local Courier / Hand Delivery'` (`:441`, same in copy text `:234`).

### H8 — Purchase receiving still unauthenticated, unchecked, double-receivable (B5, HOLDS, unchanged)
`app/actions/purchases.ts:100-172` (`receivePurchaseOrder`): no `checkAccess`, no org check, no quantity/status validation, and **none** of the four writes checks its error (`:123-160`: PO status, item `received_quantity`, batch insert, movement insert are bare `await`s). `receive-button.tsx:12-20` also ignores the returned result. Any signed-in employee can receive any PO, and clicking twice creates a duplicate batch (`${po_number}-RECV`, `:145` — no uniqueness handling) and double-counts stock. Expiry is hardcoded "+30 days for demo" (`:135-136,147`). Correction to the old report: the function *does* fetch the caller's `organization_id` (`:107-116`) and tags the batch/movement inserts with it (`:143,156`) — so the cross-tenant *write* is the PO/item status flip, not the stock insert. **Fix:** status guard (`status != 'received'`), check every write error, unique batch number, real expiry from PO/form (not the +30-day default).

### H9 — Returns still trust the client and never validate against the original sale (B6, HOLDS, unchanged)
`app/actions/returns.ts:25-154`: no check that `sale_id` exists, that the product was on that sale, that returned qty ≤ sold qty, or that `refund_amount` ≤ paid amount; `return_action` is an unchecked string; `Promise.all(tasks)` result is never inspected (`:146`) yet returns `{ success: true }`. Refunds can exceed the sale; items never sold can be restocked; the same sale is returnable repeatedly.
**Fix:** validate against `sale_items` + prior `return_items` inside a transaction; cap refund at sale total.

### H10 — Payroll regeneration still overwrites paid rows; pay still not idempotent (B7, HOLDS, unchanged)
`app/actions/payroll.ts:33-47`: `generatePayroll` upserts every active employee with `status: 'draft', deductions: 0, bonuses: 0, net = base_salary` on conflict `employee_id,month,year` — re-running it for a month already paid resets paid rows to draft at full salary. `payPayroll` (`:66-79`): no org check, no `status='draft'` guard, no payment/ledger record — marking an already-paid row paid again (or any UUID) succeeds silently. No month/year validation; attendance/deductions are never factored in. Additional suspicion (needs live DB): the upsert conflict target `employee_id,month,year` may not match any unique index — the only payroll unique index in the SQL is `(organization_id, employee_id, month, year)` (`pos-full-setup.sql:718`); PostgREST requires `onConflict` to match a unique constraint exactly, so `generatePayroll` may fail at runtime.
**Fix:** skip rows with `status='paid'` on regenerate; guard pay with `.eq('status','draft')` and check row count; validate month 1–12; fix the conflict target to include `organization_id` and live-test Generate.

### H11 — Middleware still trusts cookie-name presence; still fails open on missing env (S3, HOLDS, unchanged)
`lib/supabase/middleware.ts:12-24`: `hasAuthCookie` only checks a cookie name starts with `sb-` and contains `-auth-token`; `:34-36` prefetch requests carrying such a cookie skip `getUser()` entirely (fast path 3). `:40-44`: missing `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` logs and returns `NextResponse.next()` with no redirect. `dashboard.ts:8-16` still fetches the profile but never rejects a null one, and its `sales`/`sale_items`/`categories`/`products` queries (`:41-76`) have no org filter.
**Fix:** validate the session (`getUser()`) on every non-public request including prefetches; fail closed (redirect to an error/login page) when env is missing.

### H12 — IDOR on updates/deletes by bare `id` still present (S5, HOLDS)
Verified still bare-`id` only, no `.eq('organization_id', …)` on the write: `inventory.ts` `updateCategory`/`deleteCategory` (`:50-81`), `updateProduct`/`deleteProduct` (`:147-227`); `vendors.ts:88-97` `updateVendor`; `payroll.ts:71-76` `payPayroll`; `tasks.ts:93-99,112-118` `updateTaskStatus`/`deleteTask`. Any authenticated user who knows/guesses a UUID can modify or delete another tenant's records.
**Fix:** add `.eq('organization_id', profile.organization_id)` to every update/delete and check the affected-row count.

## Medium

### M1 — FBR fields are storage-only: nothing in the app can ever populate them (NEW, e35d033)
Grep: no code writes `fbr_status`, `fbr_reference_no`, `fbr_response_code/message`, or `fbr_submitted_at` — `processCheckout` doesn't set them (relies on DB default `'Pending'`). No FBR submit action/endpoint exists. Every invoice therefore stays `Pending` with placeholder response text and no QR forever, unless someone writes the DB by hand. Null-handling itself is good (`fbr-invoice-client.tsx:165-169,261,570`: status defaults to `'Pending'`, QR only when a reference exists, `[System timestamp]` placeholder).
**Fix:** build (or explicitly scope out) the FBR submit step that writes these four columns + status transition, with `Pending → Submitted/Failed` guarded.

### M2 — `amountInWords` has four verified bugs (NEW, lib/amount-in-words.ts — executed against the real file)
`lib/amount-in-words.ts:60-79`, tested with Node 24: `0.995` → "…Zero and **One Hundred Paisa** Only." (paisa rounds to 100, never carried into rupees); `1.005` → "One Only" (binary float makes paisa 0 — paisa silently lost); `1234567890123` → "One Two Hundred Thirty-Four Billion …" (SCALES stops at Billion, index 4 is undefined → trillion scale silently dropped, amount mis-stated); `-500.75` → "Negative Five Hundred Only" (negative branch rebuilds words without the paisa clause). Correct cases verified: 0, 138980 (exact sample text), 1234567.89, 1.5bn.
**Fix:** round the whole amount to paisa first (`Math.round(abs*100)`), carry paisa==100, extend SCALES (Trillion+), include paisa in the negative branch.

### M3 — Low-stock is effectively dead: `minimum_stock_level` defaults to 0, so LOW never fires (NEW, 7dfa641)
`radars.ts:238-248`: threshold is the 10 fallback only when min is `null/undefined`, else `Number(min) || 0`. But `createProduct`/`updateProduct` store `0` when unset (`inventory.ts:138,177`), and the schema is `integer not null default 0` (`pos-full-setup.sql:177`). So for any product without an explicit minimum, threshold = 0, `currentStock <= 0` is already OUT_OF_STOCK, and LOW can never occur. The `LOW_STOCK_THRESHOLD = 10` (`radars.ts:23`) is dead code in practice. The handover admits this, but the UI still presents "Low Stock" as a live signal. The copy also misleads: `radars-client.tsx:206` says "Low means at or below the product's minimum stock level (10 if none is set)" — the 10 fallback almost never applies.
**Impact:** the Stock radar's LOW count is 0 until someone sets a minimum per product; the client gets no low-stock warning out of the box.
**Fix:** treat `0` as unset (use the 10 fallback) or require a minimum at product creation; correct the copy once the rule is decided.

### M4 — No error boundary: any radar/dashboard query failure crashes the whole page (NEW, 7dfa641)
No `error.tsx` exists anywhere under `app/` (verified by search). `getInventoryRadar()` throws on Supabase error (`radars.ts:286`); `getBatches`/`getStockLevels` throw (`inventory.ts:243,375`); `getVendorsRadar()` throws (`radars.ts:350-351`). `RadarsDataLoader` (`radars/page.tsx:18-28`) and `DashboardDataLoader` (`dashboard/page.tsx:15-20`) have no try/catch. The `Suspense` fallback (`radars/loading.tsx`) covers loading only. `getRadarSummary` uses `Promise.all` (`radars.ts:390-394`), so one radar failure kills the whole dashboard strip and `/radars` page.
**Impact:** one failed query = Next.js default error page for the whole route, no retry or partial data. (Same pre-existing gap as B10 for all list pages.)
**Fix:** add `error.tsx` under `(dashboard)` and/or catch per-radar and render an error state with retry; use `Promise.allSettled` + per-radar fallbacks.

### M5 — Dashboard strip and KPI card disagree on "expiring within 30 days" (NEW, 7dfa641)
Strip urgent = `URGENT + EXPIRED` where URGENT is `daysLeft < 30` i.e. 0–29 (`radars.ts:174-180,404-406`). KPI "Expiring Batches" uses `Math.ceil((exp − now)/86400000) <= 30` (`dashboard.ts:175-186`) — includes a batch expiring in exactly 30 days and counts expired batches of any age. Same page shows two different "30-day" numbers; the underlying `days_left` values also come from different formulas (midnight-floor in `radars.ts:166-172` vs ceil-from-now in `dashboard.ts`). Near midnight the two disagree by 1 day.
